# Workflow definitions and role relationships

`software-delivery` defines a delivery flow shared across POCs. A work item supplies its ID, evidence scenario, permitted files, candidate changes, expected baseline failure marker, and acceptance command. PAY-482 is one input. The flow includes Evidence Gate, Knowledge Team, Planner, Orchestrator, Architect, parallel Coder/Infrastructure/Integration, restricted Candidate Change, deterministic Candidate Verification, parallel Testing/Security/Reliability, Reviewer, Risk & Approval, and the human review gate.

The Agno adapter applies the work item's candidate change to an isolated workspace for each run, without modifying the mounted source. The PAY-482 example first uses a regression test to demonstrate the baseline failure, then applies the work item's change and reruns the tests. Passing results proceed to expert verification and human review. The work item supplies the candidate change and the Coder Agent reviews it and provides recommendations. The POC does not yet have the LLM generate an executable patch. External tickets, CI, approval, and deployment remain disconnected.

The original design also includes rework after failed review, reassignment after failed verification, Release → Documentation → knowledge ingestion after human approval, and lateral Knowledge support. These are future capabilities. The current workflow stops before human review, treats failures or missing evidence as incomplete, and does not automatically retry assignments, release, or write to a Wiki. `continuous-improvement` consists of Observability Team, Governance Team, Improvement, and Optimization, and produces an improvement draft.

The `ref` values of workflow `executor` and `condition` steps identify capabilities. Each runtime adapter implements the corresponding behavior and must pass the same cases. Team member lists describe possible delegation. Actual calls are recorded in each run.

An example shared work item contract is in `scenarios/pay-482/work-item.json`. `id` identifies the input work, `evidence.scenarios` supplies its evidence fixtures, `candidate.files` restricts editable relative paths, `candidate.changes` describes replacements that must match uniquely, `candidate.expected_baseline_failure` specifies the expected baseline failure, and `candidate.test_command` defines a test command without a shell. A new POC adapter maps the same contract to its own workspace, change application, and test command without copying workflow and agent definitions into a case-specific version.
